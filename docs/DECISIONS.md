# Implementation decisions

- The isolated project was initialized from the supplied specification in a new directory. Public commits use the project name and a non-personal commit address.
- Each result database contains one scan. The walker allocates monotonically increasing node IDs with parents before children. A later directory observation can attach an enumeration error to the same node.
- On Linux the path type retains filename bytes. On Windows it retains UTF-16LE code units, including unpaired surrogates. Display formatting escapes malformed characters and controls. File operations use the original representation.
- Scan batches are borrowed by a synchronous sink. The consumer can write immediately or copy into a bounded queue. The scan control is owned by the worker; it outlives the walker and control thread.
- SQLite is statically linked from an independently hash-checked upstream amalgamation. GTK is a GUI build dependency only. The Ubuntu build consumes distribution runtime libraries and records the corresponding distribution package versions.

- Successful finalization commits the terminal run state and the active aggregate generation together. A cancellation preserves committed observations and makes post-exit aggregation an explicit DB-only action. After worker loss, the controller reads the actual committed metadata even if a commit notification was missed.
- Import validates an untrusted standalone snapshot and creates a validated private backup for the explorer. All view queries use the private copy. Snapshot output with an existing SQLite journal is rejected before replacement.
- Scans automatically exclude the configured cache base. The UI maintains expanded tree state during collection and offers an explicit refresh. Allocated GTK page-cache memory is estimated across active lists. The headless paging probe and the desktop targets are reported separately.
- Both platforms overlap at most one helper metadata operation with enumeration in the standard profile. The conservative profile uses synchronous metadata reads. Windows still relies on path-based Win32 enumeration, with the remaining ancestor race documented in the limitations.
- The open-source release is a preview. Remaining acceptance checks and missing v1 features are recorded in the validation and limitations documents.
- A scan cache contains a lease file held by both controller and worker. A restarted app takes an exclusive lease before opening committed rows and keeps it while the recovered result is displayed. A running cache whose process has exited is recorded as interrupted when SQLite can write the marker. Markerless 0.1.0 caches are skipped; their standalone snapshots remain importable.
- The explorer captures the export scope, filters and explicit selection when opening the save dialog. A folder selection traverses saved parent links. A filtered export applies the active filters across all pages. The volume card uses one OS measurement stored by the worker at scan start.
- Windows cache I/O uses extended paths, SQLite's win32-longpath VFS and native directory enumeration. Recovery uses local, private user cache directories.
- Cache retention runs during background startup recovery, before starting a scan, and before creating a private copy of an imported snapshot. Retirement requires an exclusive lease, an ownership marker bound to the result file's identity, and a small allowlist of internal files. Active and displayed caches retain their lease. The latest recoverable managed scan is reserved. The remaining idle managed caches are subject to best-effort boundaries of 30 days, 10 directories and 8 GiB of summed file lengths.
- Diagnostic export uses one read transaction for the scan metadata and issue totals, then publishes through the same atomic output path as result export. It uses typed status and reason codes. It does not copy log text or arbitrary settings. The sole path opt-in adds the scan root as displayed in the app for one export.
- The Windows worker uses the Windows subsystem and reads and writes the same inherited binary pipes. The CLI uses the console subsystem.
- The live folder tree uses ascending observation IDs so later commits append visible rows without recreating expanded rows. The UI polls the existing commit sequence and refreshes expanded lists in batches. A bounded preview reads the first page of the focused folder for the live treemap. The final view switches to metric sorting after worker exit.
- Windows standard mode overlaps the walker and helper on adjacent file metadata queries, respecting its two-operation limit. Results are emitted in observation order. Both outstanding operations finish before a pause acknowledgement. Conservative mode keeps one active operation. Win32 directory enumeration requests the larger buffer when supported.
- Windows access-denied rows offer a command for the selected path, with native path bytes encoded separately from PowerShell syntax. The user opens the administrator terminal and runs the command. A directory retry writes a separate snapshot. A file retry displays metadata for the selected path.
- Windows collection passes owned batches to one SQLite writer, with at most eight batches and 16 MiB retained across the queue and active write. Backpressure limits collection. The walker drains outstanding writes before acknowledging a pause and joins the writer before finalizing. The conservative traversal still issues one target metadata operation at a time.
- The scan cache batches passive WAL checkpoints while retaining the observation commit cadence, disk-space checks and headroom for reclaiming WAL space. Collection uses SQLite's `NORMAL` synchronization. Committed WAL survives worker-process exit. Sudden OS or power loss can lose recent transactions before the next sync. For automatic Windows finalization, the worker switches to `FULL` before the terminal transaction and leaves its synced pages in the private cache WAL. Other finalization paths keep the terminal checkpoint. Readers resolve committed cache pages through SQLite, and export uses the SQLite backup API to produce a standalone snapshot. The private temporary snapshot uses a memory rollback journal and retains a full database sync before publication. [SQLite WAL and checkpointing](https://sqlite.org/wal.html) · [SQLite synchronization modes](https://sqlite.org/pragma.html#pragma_synchronous)
- On local NTFS, the walker can retain a verified directory handle and open an ordinary file relative to it using the exact UTF-16 component, metadata-only access and no-recall/no-reparse flags. A single metadata query supplies a single-link file's sizes, timestamps, link count and 64-bit NTFS ID. The stored identity uses the verified parent volume and the equivalent 128-bit NTFS representation. If a successful relative open needs the full ID or separate metadata queries, those checks use the open file object. Files enumerated with special allocation attributes and failed relative opens use the established pathname measurement. The directory cursor, retained metadata handle and temporary checks share the directory handle budget. The walker rechecks the selected path between delivered batches, before entering directories and at enumeration end. A rename detected after observations were delivered marks coverage partial. The original pathname enumeration still has a race between checks. [Microsoft NtOpenFile](https://learn.microsoft.com/en-us/windows/win32/api/winternl/nf-winternl-ntopenfile) · [Microsoft file-open flags](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/nf-ntifs-ntcreatefile) · [Microsoft NTFS ID representation](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-fsa/4e3695bd-7574-4f24-a223-b4679c065b63)
- On Windows the worker link lists `metadata.c` and `walk.c` objects explicitly in that order before the archives. The same objects are archived into the platform library for other targets. The explicit layout reproduced the hardlink handle-reuse benefit in the tested UCRT64 Release build. Linux keeps its platform archive layout.
- The Windows walker resolves the native NTFS relative-open functions once after checking the root and before starting any metadata helper. Failure to resolve the functions selects the pathname measurement path. The relative open retains the metadata access and no-recall/no-reparse flags and uses the verified directory handle.
- Finalization inserts leaf aggregates in bounded SQLite ranges using the stored unsigned byte encoding and existing hardlink representative rows. Directories still use checked C sums. The active generation changes only after the aggregate row count matches the observation count. The CLI waits on a worker-exit notification between interrupt polls, and a finished snapshot wakes its interrupt-monitor thread immediately.
- The Windows worker's managed cache can sync the committed WAL every 512 new frames through the SQLite VFS without rewriting the database pages then. It attempts backfill and reclamation at 4,096 WAL frames or sooner when the cache space check needs to recover space. If direct WAL sync is unavailable, the writer uses the existing passive checkpoint. If a pinned reader prevents that checkpoint from finishing, the writer still syncs the WAL and updates the maintenance interval only after success. The total cache budget applies throughout. Standalone saves still use the SQLite backup API and full publication sync. [SQLite WAL and checkpointing](https://sqlite.org/wal.html) · [SQLite journal-file control](https://sqlite.org/c3ref/c_fcntl_begin_atomic_write.html#sqlitefcntl_journal_pointer)
- The Windows walker extends its bounded UTF-16 path buffer in place and restores the parent length after measuring a leaf. The standard worker's metadata helper owns a separate copy of its path. The raw observed name and path limits use the existing validation rules.
- The Windows controller launches the installed sibling worker directly with `CreateProcessW` and an explicit handle list for standard input, standard output and discarded standard error. The controller ends of the pipes remain noninheritable. The worker uses the existing framed protocol, and the controller still waits for its process to exit. Linux continues to use GIO subprocesses. [Microsoft process creation](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) · [Microsoft handle inheritance](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)
- A managed Windows cache checks WAL counters before attempting passive backfill. It omits the extra explicit WAL sync only when the checkpoint succeeds, the sole writer observes the same known WAL frame count before and after, and the backfilled frame count increases. The pinned SQLite implementation syncs the complete stable WAL before publishing that progress. Errors, invalid or changed counts, and incomplete checkpoints without progress retain the explicit sync fallback. The 512-frame maintenance interval, reclamation threshold, final `FULL` transaction and SQLite-backup publication barriers remain unchanged. The regression forwards real `FlushFileBuffers` calls and observed two WAL flushes before this guard and one afterward; it does not simulate power loss. [SQLite checkpoint API](https://sqlite.org/c3ref/wal_checkpoint_v2.html) · [SQLite WAL durability](https://sqlite.org/wal.html)
